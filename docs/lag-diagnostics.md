# 共享增强双端诊断

共享增强 0.5.1 的「高级 → 诊断（屏幕、声音、快捷键）…」可连接当前 Crisp。
在 Crisp 开启原有远程音频服务即可；主控扬声器/麦克风不必开启，诊断不会主动启动采集设备。

- 同一 TCP 49555 监听器按第一帧区分音频与诊断；原音频 v1 保持兼容。
- 诊断前言：`uint32_be length + SSE-CRISP-DIAGNOSTICS/1`；后续同样长度前缀的 JSON，最大 64 KiB，`version=1`、UUID 会话编号，开始时选 screen/audio/both，时长 1–60 秒。
- 客户端消息：start、ping、pattern、patternStop、stop。服务端消息：started、pong、sample。每秒资源快照；音频路径只在音频诊断开启时累计有界计数和直方图。不同主机时钟保留偏移误差，不声称精确单向延迟。
- 主控必须明确启动短测才出现图案窗口；图案显示在 mini 鼠标所在显示器，走已有屏幕共享，不开第二路远程视频，不执行任意输入或抓取 mini 业务截图。
- 主控断开、服务关闭、睡眠时回收；mini 独立 60 秒上限，图案 5 秒无请求自动关闭。服务菜单显示正在诊断。
- 默认没有诊断采样器/计时器/连接/图案窗口。开启后最多一个诊断会话、每秒 30 条请求、三个待完成发送；超过限制关闭诊断，不影响音频连接。资源读取及报告序列化在单独队列完成，不占用音频发送队列。

覆盖相关进程 CPU/内存/磁盘、系统 CPU、温度压力/交换空间、接口类型和控制请求往返；音频覆盖发送间隔/积压、采集缺帧/回调年龄、麦克风排队/丢弃及 HAL 写入。不能据此断言屏幕编码/解码耗时、实际音频 TCP 重传或通话应用已消费音频，缺失项保留在报告中。

资源口径：进程 CPU 的 100% 表示一颗逻辑核心；磁盘字节为两次采样间的差值。
兼容现有 0.5.1 报告的 `residentBytes` 字段实际取自 `ri_phys_footprint`，表示物理内存足迹，
不能与外部工具的 RSS 直接比较。系统不允许读取的进程计数必须保留缺口，不能按零值判断。

端口沿用现有可信局域网边界，无新增认证/TLS，不应直接暴露公网。主控报告只含数值，不含录音或截图。

离线验证使用 `CRISP_CONTROLLER_SOURCE=<共享增强仓库> scripts/check-remote-audio.sh`；只有 Command Line Tools 时设置 `DEVELOPER_DIR=/Library/Developer/CommandLineTools`。用真实 TCP 服务及合成音频后端，不安装或启动硬件设备。完整应用构建是 `make compile`，不是会替换已安装应用的 `make dev`。

显式增加 `--full-lifecycle` 会实际等待一分钟，并在 mini 本地手动触发图案组件验证
（颜色编码、停止和无指令自动关闭），不创建远程视频、不采集音频。
普通调用不会显示图案；这项本地验证不能替代 MacBook 的窗口采样与真实共享链路验收。

## 双机联调进度（2026-10-29）

MacBook 已恢复在线，用户使用共享增强 0.5.1 返回两轮 60 秒报告。
第一轮按步骤关闭主控声音，第二轮用户明确确认扬声器开启、麦克风关闭，并能听到 mini 播放的声音。
这两轮没有由助手启动新的测试音；第二轮 mini 的具体播放内容未固定，不能视为完全受控的音频对照。

| --- | --- | --- |

两轮均获得真实双端数据与图案响应；报告结束后的 mini 只读检查仅见 TCP 49555 监听，
没有残留的已建立连接。第二轮的播放计数证明软件路径频繁耗尽缓冲及清空积压，
但不能仅凭摘要判定原因在 Wi-Fi、mini 发送调度还是 MacBook 播放调度。

摘要中的 CPU 是最后一次资源快照；诊断往返值取时钟估计误差最小的一次，均不是全程平均或峰值。
mini 三个进程资源不可读已明确报告，不能按零值判断；61/59 的快照数量差异也不能直接解释为网络丢包。
