## 当前证据及边界

1. 第二次连续音期间，现有 Crisp TCP 会话 35 个一秒采样始终为 Established。
   相邻首尾计数相减：发送 1,815,024 字节、重传 32,812 字节、接收乱序 9,650 字节。
   每秒观测的平均 RTT 范围为 9.75–75 ms。这证明存在重传和时序抖动，
   不能据此把重传比例等同于丢包率，也不能把每个听感断点直接归因于网络。
2. 对实际 `CrispAudioResampler` 输入连续合成波形，按 20 ms 分块与一次性转换比较。
   44.1/48/96 kHz → 24 kHz 均每块输出 480 帧，分块结果与整体转换逐样本差值为 0，
   当前 packet 补齐逻辑没有额外插入静音。该检查未覆盖实际 tap IO 调度、环形队列欠载。
3. 只抓取并读取主控最新提交 `1197586d441f3cddb6e4623fd955fdc0a6e9fbef`（0.4.4），
   没有合并或覆盖 `/Users/cd03/workspace/ScreenSharingEnhancer` 的已有未提交修改。
   最新 `AudioIO.swift` 起播无预缓冲，以 `.dataPlayedBack` 回调减少待播包计数，
   达 5 包就 `stop()/play()`。Apple SDK 的 `AVAudioPlayerNode.h` 明确：
   `.dataPlayedBack` 包含输出设备播放延迟，`.dataRendered` 不包含下游处理/硬件延迟。
   因此旧队列存在把设备延迟算作应用积压而频繁清空，以及短暂到包延迟时直接欠载的风险。
   尚无主控运行时的清空次数统计，不能说这已经被证明是唯一根因。

## 主控候选修复

在独立检出副本实施，原主控工作目录保持原样。Crisp 源码、已安装应用、HAL 组件、
默认音频设备、虚拟屏和分辨率均未更改。

- 保留连续 3 包（60 ms 音频）后起播，以吸收短暂网络/任务调度抖动。
- 以 `.dataRendered` 统计尚未渲染的音频，避免把耳机播放延迟算作积压。
- 真正欠载后暂停并重建缓冲，再继续播放；不会收到一包就立刻开始播放。
- 约 100 ms 的应用队列上限保留，真实超限时清空旧队列并切换 epoch，旧回调失效。
- 固定 TCP 49555、消息格式、24 kHz 单声道 PCM16、独立麦克风开关均未修改。

修复代码：[共享增强 0.4.5](https://github.com/forvey/ScreenSharingEnhancer/commit/7b85eef810f6ea1316563875d2c91ae36bdd7e97)。
